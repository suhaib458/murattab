# TTU Table Geometry Parser — مُحلل هندسة جدول جامعة الطفيلة

## الهدف
تحويل المخرجات المكانية للتعرف البصري المحلي (`OcrImageResult`) إلى بنية جدولية هندسية دقيقة وحتمية (`TtuTableGeometryResult`):
`كلمات/أسطر OCR مع الصناديق المحيطة ← عناوين الأعمدة ← حدود الأعمدة الأفقية ← صفوف المواد ← الخلايا ← المقاطع الرأسية للخلايا`

---

## عقد المدخلات والمخرجات (Contract)

### المدخل: `OcrImageResult`
- يعتمد حصراً على الأنواع المملوكة لمرتب في `src/domain/ocr/types.ts`.
- جميع الإحداثيات تكون مسبقاً بنظام إحداثيات الصورة الأصلية المرفوعة.

### المخرج: `TtuTableGeometryResult`
```typescript
interface TtuTableGeometryResult {
  columns: TtuTableColumn[];
  rows: TtuTableRow[];
  issues: TtuTableParseIssue[];
  confidence: number;
}
```

## المبادئ الهندسية الأساسية

### 1. هندسة الكلمات هي المصدر الحقيقي لمحتوى الخلايا (Word Geometry as Truth)
- لا يتم الاعتماد الأعمى على نص السطر الكامل (`OcrLine.text`)؛ حيث قد يجمع محرك Tesseract كلمات من عدة أعمدة (مثلاً: اسم المادة + الموعد + القاعة) في سطر بصري واحد.
- يتم إسناد كل كلمة `OcrWord` إلى عمودها المستهدف بناءً على مركزها الأفقي `(x0 + x1) / 2`.
- يُعاد بناء محتوى الخلية حصراً من الكلمات المنتمية إليها مع الحفاظ على الترتيب المنطقي للعبارات المختلطة مثل `ICT - 4` و `DS-ICT 3` و `10:00 - 11:00`.

### 2. استقلالية المقاييس والدقة (No Fixed Pixel Tolerances)
- لا تُستخدم أي ثوابت بكسلية مطلقة (مثل 10px أو 20px).
- تُشتق كافة هوامش التسامح والفواصل من مقاييس الصورة النسبية:
  - الوسيط الحسابي لارتفاع السطر (`medianLineHeight`).
  - أبعاد وارتفاع صف العناوين.
  - نسب أبعاد الصورة وعروض الأعمدة.
- يعمل المحلل بنفس الدقة والتطابق التام على الصور بمختلف الأحجام (مثل `800×400` و `1600×800`).

### 3. استكشاف العناوين بدليل النطاق الرأسي (Band-Level Header Evidence)
- الكلمات والأسماء القصيرة المنفردة (مثل «مادة»، «شعبة»، «قاعة»، «وقت») **لا تنشئ جدولاً بمفردها**.
- يتطلب التعرف على العناوين وجود عنقود رأسي متقارب يحوي عناوين أعمدة متعددة، مع اشتراط وجود العناوين الأساسية (`courseName`، `meeting`، `room`).
- في حال غياب العناوين الأساسية، يُرجع المحلل خطأ `HEADER_NOT_FOUND` بنسبة ثقة 0 دون اختلاق جدول غير موجود.

### 4. دعم الجداول العربية (RTL Physical Layout)
- يتم ترتيب الأعمدة فيزيائياً من اليسار إلى اليمين حسب إحداثيات X (`x0` تصاعدياً).
- هذا يضمن معالجة موثوقة لكافة تنسيقات البوابة الجامعية سواء بدأت من اليمين أو اليسار دون افتراض ترتيب نصي مسبق.
- حدود الأعمدة (`xStart..xEnd`) تُحسب عند نقطة المنتصف بين مراكز العناوين المتجاورة.

### 5. استراتيجية ارتكاز اسم المادة (Course-Name Anchor)
- يُعد عمود `courseName` المرتكز الأساسي لتحديد الصفوف.
- يتم تجميع كافة الجلسات المرتبطة بالمادة الواحدة (مثل المحاضرة والمختبر: سطرين للموعد وسطرين للقاعة) داخل صف واحد `TtuTableRow`.
- تمتد حدود الصف رأسياً لتشمل كافة الجلسات التابعة للمادة حتى بداية المادة التالية.

### 6. الحفاظ على المقاطع الرأسية داخل الخلية (Multi-Segment Cells)
- تحافظ كل خلية `TtuTableCell` على أسطرها الرأسية عبر مصفوفة مرتبة `segments: TtuCellSegment[]` من الأعلى إلى الأسفل.
- يحتوي الحقل `rawText` على النص الكامل مع فواصل أسطر `\n` بين المقاطع دون فقدان الترتيب.

### 7. استبعاد تذييل الصفحة (Footer Cutoff)
- يتم التعرف على نهاية الجدول واستبعاد أي نصوص سفلية خارج الجدول (مثل تواريخ الطباعة، أرقام الصفحات، ملاحظات العمادة) عبر فحص الفجوات الرأسية ومطابقة الأعمدة.
- يُسجل التحذير `FOOTER_DETECTED` عند استبعاد تذييل الصفحة.

### 8. أمان نصوص Bidi والنص الخام
- تُزال أحرف التحكم الاتجاهية (LRM, RLM, LRE, PDF, إلخ) وتُطبّع الحروف **حصراً لغايات المقارنة والبحث**.
- النص الخام المخزن في الخلايا والمقاطع يبقى مطابقاً تماماً لمخرجات الـ OCR الأصلية.

## القيود الصريحة للمرحلة الثانية (Phase 2 Limitations)

> [!IMPORTANT]
> هذه المرحلة معنية بـ **هندسة وهيكل الجدول فقط**.

- **لا يوجد تفسير لأيام الأسبوع** («ح» لا تُحوَّل إلى الأحد، «ن» لا تُحوَّل إلى الاثنين).
- **لا يوجد تفكيك للأوقات** («10:00 - 11:00» لا تُحلل إلى startsAt / endsAt).
- **لا يوجد توسيع للقاعات** («207 م» لا تُحوَّل إلى «مجمع القاعات»).
- **لا يوجد تصنيف للمحاضرات والمختبرات** (ICT لا تُصنَّف كمختبر هنا).
- **لا يوجد توليد لكائنات DraftCourse**.
- **لا يوجد ربط بواجهة المستخدم (Smart Import UI)**.
